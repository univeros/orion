# Decisions log

Append one entry per decision: date, work package, decision, reason, alternatives rejected.

- 2026-10-25 · WP0 · Orion is built framework-agnostic from the start, modelled on `polaris-core`: a framework-free core with ports and defaults, host integrations as packages. · Reason: the Polaris extraction cost a full program; the ports Orion needs (storage, dispatcher, tenancy, signer, clock, logger) are few, and its hard parts never touch a framework. · Rejected: Univeros-only, extract later.
- 2026-10-25 · WP0 · One repository, `github.com/univeros/orion`, holds every package including the Univeros module (`packages/univeros`); packages are split-published later to `univeros/orion.<package>`. · Reason: avoid the `univeros/polaris` + `univeros/polaris-core` split, where the module lags the core and is proven separately; one CI run proves the module on every PR, one version line. · Rejected: a second repository for the module.
- 2026-10-25 · WP0 · Composer vendor `orion-search`, PHP namespace `Orion\`; the module is `univeros/orion` under `Univeros\Orion\`. The root manifest is `univeros/orion-monorepo` because a root package cannot require a path package of the same name. · Reason: the Packagist vendor `orion` is owned by a third party (`orion/cep`, 2017); `orionphp` is taken; `orion-search` and `orion-php` were free on 2026-10-25. · Rejected: `orion` (unavailable), `univeros/orion-core` for the agnostic packages (ties the agnostic library to the framework's name).
- 2026-10-25 · WP0 · MIT for every package, the module included. · Reason: the module is glue with no competitive value in hiding, and the framework is MIT; a proprietary package inside a public MIT monorepo is awkward. Reversible per package until the first tag. · Rejected: proprietary module as `univeros/polaris` is.
- 2026-10-25 · WP0 · The storage port must run on the host's live database connection, and `Outbox::record()` runs inside the caller's transaction; a storage conformance test enforces it. · Reason: the lossless-reindex claim (v1 §8.3) holds only if the outbox commits with the entity write; the second-connection workaround `univeros/polaris` uses would silently break it. · Rejected: a dedicated Orion connection beside the ORM's.
- 2026-10-25 · WP0 · Core owns receipt signing (Ed25519 via libsodium, `kid`) and an append-only hash-chained `orion_receipt` table. · Reason: the framework has no append-only event log and `univeros/security` is a symmetric encrypter only, so v1 §11's reuse assumption does not hold even inside Univeros. · Rejected: depending on a framework event log.
- 2026-10-25 · WP0 · Tenancy is an explicit choice at boot: `Tenancy::single()` or a `TenantResolver`; no implicit default. · Reason: a forgotten tenant filter leaks data; the config must make the single-tenant case a visible decision. · Rejected: defaulting to single-tenant.
- 2026-10-25 · WP0 · The `search:` YAML is a runtime manifest loaded by core (the `polaris/core` `api/**/*.yaml` model); the byte-stable Action/Input/Responder/SDK slice is emitted only by the Univeros module. · Reason: code generation into a host's shape is host-specific; loading at runtime works in every host. · Rejected: generation in core.
- 2026-10-25 · WP0 · PHPStan level 8, PSR-12, PHPUnit 12, PHP >= 8.3 with the platform pinned to 8.3.0. · Reason: greenfield; matches `univeros/framework` (level 8) rather than `polaris-core` (level 5). · Rejected: level 5.
- 2026-10-25 · WP0 · The split workflow is not configured yet. · Reason: the owner asked to split later; the package-to-repository map (`univeros/orion` the module to `univeros/orion.univeros`, the rest to `univeros/orion.<package>`) is recorded here so the workflow is a copy of `polaris-core`'s `split.yml` with an explicit matrix when the time comes.
- 2026-10-25 · WP0 · No pull requests and no co-authored commits: work lands on `main` in commits authored by the owner alone; acceptance is recorded in the epic's closing comment. · Reason: owner's workflow; the repository has one author. · Rejected: the `polaris-core` branch-and-PR convention.
- 2026-10-25 · WP1 · The `Storage` port takes the `polaris/core` `DatabaseAdapter` criteria grammar: criteria are `column => value`, ANDed; a scalar is equality, a list is IN (an empty list matches nothing), null is IS NULL, and a typed `Orion\Storage\Condition` is a comparison (`lt`, `lte`, `gt`, `gte`, `ne`, `notNull`); comparing against NULL never matches, as in SQL. Values crossing the port are scalars, null and `DateTimeImmutable`; adapters return raw driver values. Methods: `findOne`, `findMany` (order, limit, offset), `insert`, `update`, `delete`, `count`, `transaction(callable)` (a savepoint when nested, rollback when the callable throws). `dialect()` and `Increment` are left out. · Reason: proven in polaris across in-memory, PDO and Cycle adapters; it is enough for outbox, registry, alias and receipt access, and small enough that every host connection (PDO, Cycle `DatabaseInterface`, DBAL, Laravel) can implement it on its live connection, which the same-connection invariant needs. No core code generates SQL, so `dialect()` belongs to the `pdo` installer; outbox offset allocation is designed in WP4 and adds `Increment` or its own primitive then. · Rejected: an expression tree with OR and LIKE (no core caller needs it, and every adapter would reimplement it), raw SQL through the port (breaks non-PDO hosts).
- 2026-10-25 · WP1 · `Document::$version` is a plain non-negative `int`, the outbox offset. · Reason: v1 §8.3 and §13 define the version as the outbox offset and use it only for ordering; it maps one to one onto engine external versions (Elasticsearch and OpenSearch `version_type=external` are non-negative longs, Solr `_version_`), and a value object would add no invariant beyond `>= 0`. · Rejected: a `Version` value object.
- 2026-10-25 · WP1 · "ASTs round-trip through their builders" means: the fluent builder and the declarative form (`Query::fromArray()`, `IndexSchema::fromArray()`) produce equal ASTs, and `fromArray(toArray())` is the identity. The declarative readers refuse unknown keys and name the path of the first bad value (`query.filters[0].type`). · Reason: v1 §5 promises declarative construction for agents and §12 loads schemas from `search:` YAML; a typo that silently drops a filter or a field is the failure mode to rule out. · Rejected: ignoring unknown keys; a separate DTO layer for agents.
- 2026-10-25 · WP1 · `IndexSchema::native(string $engine, array $settings)` stores plain data per engine name, replacing earlier settings for that engine. · Reason: the plan is a pure diff (v1 §8.1) and receipts carry a schema hash (§11); a closure, as in the v1 §6 sample, can be neither hashed, diffed, nor loaded from a manifest. · Rejected: a callback receiving the engine's mapping builder.
- 2026-10-25 · WP1 · Schema change classification: a new field (sub-fields included) is additive; every other difference to index state is breaking (removal, type, language, folding, any flag, vector dims or metric, object to nested). Query-time attributes (`boost`) are not index state, no engine can report them, and they are left out of the diff, so a boost change never shows as drift (it takes effect when queries compile from the registered schema). Adapters report a native type with no neutral equivalent as `FieldType::Unknown`, never declarable at any depth, so any plan touching it is breaking. Object fields are diffed by dotted path. A missing live index plans every field as added. · Reason: v1 §8.1 requires total classification failing closed; classifying by "only additions are additive" makes any attribute added later breaking by construction. Flag changes are breaking because Elasticsearch cannot enable `doc_values` or indexing in place, and core classifies once for every engine. The org key and native settings are not diffed in WP1 (`LiveSchema` carries neither); WP3 diffs them against the registered schema and fails closed. · Rejected: per-engine classification in adapters (orchestration in adapters); classifying a boost change as additive (a plan that can never become empty); treating flag removal as additive.
- 2026-10-25 · WP1 · The four lexical verbs are one `Clause` value with a `ClauseKind` (`match` is a reserved word in PHP, so `Match` cannot be a class), and a query's clauses and filters are conjunctive. `vector()` holds one k-NN clause; `fusion` is null unless set, and WP8 decides the default when both lexical and vector retrieval are present. Offset pagination only; cursor pagination joins with WP8 query hardening behind `Capability::CursorPagination`. Sorting defaults to ascending; relevance is `Sort::SCORE` with an explicit direction. · Reason: the smallest AST covering v1 §5's list; conjunction is the common case and the only one every engine compiles identically. · Rejected: a class per lexical verb; implicit should-semantics.
- 2026-10-25 · WP1 · Reciprocal rank fusion in core is deterministic for identical inputs: rankings are summed in source-name order (float addition is not associative), a duplicate inside one ranking counts once at its best rank and does not consume a rank, equal scores break by id in byte order, and the `FusionTrace` lists every contribution by source then rank. `Fusion::weighted()` exists in the AST for engines with native hybrid fusion, and core refuses to compute it with `UnsupportedClause` (`Capability::HybridFusion`). · Reason: v1 §5.1: rank fusion is the only portable promise; score magnitudes are not comparable across retrievers, so core must not pretend to weigh them. · Rejected: normalised-score fusion in core.
- 2026-10-25 · WP1 · `Config` lands with `Storage`, `EngineRegistry` and `Tenancy` required (no defaults, no nulls) and the PSR ports (`ClockInterface`, `LoggerInterface`, `EventDispatcherInterface`, `CacheInterface`) plus `manifestDirectories` nullable with core defaults (system clock, `NullLogger`, null dispatcher, in-memory cache, `api`). `Dispatcher`, `ReceiptSigner` and `Metrics` join `Config` in WP4 as nullable named parameters, a non-breaking addition; the dev `InMemory` engine lands in WP2 with the engine conformance suite. · Reason: PSR shapes are fixed; the Orion-owned port contracts are designed with the outbox drain and receipts, and defining them now would freeze guesses. · Rejected: placeholder interfaces for the WP4 ports.
- 2026-10-25 · WP1 · Booting without a tenancy choice fails in PHP itself: `Config::$tenancy` is a required, non-nullable constructor parameter, and `Tenancy` has a private constructor with exactly two factories, `single()` and `resolvedBy(TenantResolver)`. `TenantResolver::resolve(): TenantScope` is the provisional port shape; WP6 may revise it with `ScopeInjector`. · Reason: the type system makes "no choice" unrepresentable without a runtime check to forget. · Rejected: a runtime check over a nullable parameter; an environment-variable default.
- 2026-10-25 · WP1 · `EngineRegistry` takes engines as named variadic arguments (`new EngineRegistry(elasticsearch: $adapter)`) typed `SearchAdapter&SchemaAdapter&WriteAdapter`. · Reason: PHP enforces the intersection type natively, which a phpdoc-typed array cannot; no fourth "Engine" interface is needed. · Rejected: an `Engine` interface extending the three roles; an array checked with `instanceof` at runtime.
- 2026-10-25 · WP1 · `IndexName` accepts lowercase ASCII letters, digits, `_` and `-`, starting with a letter or digit, at most 255 bytes. · Reason: the intersection of Elasticsearch, OpenSearch, Solr and Meilisearch naming rules, so a name valid in one engine is valid in all. · Rejected: per-adapter validation.
- 2026-10-25 · WP1 · Orion's tables are data in `Orion\Storage\Schema` (`orion_outbox`, `orion_index`, `orion_alias`, `orion_receipt`); their columns are provisional until the WP that first writes them (outbox and receipts in WP4, registry and alias in WP3) and may change without migration before the first tag. The conformance case publishes its own entity table as data so an adapter's test installs it beside Orion's. · Reason: installers (WP2) need the shape; nothing has installed it yet. · Rejected: SQL DDL in core.
- 2026-10-25 · WP1 · `orion-search/testing` requires `phpunit/phpunit` (^12.5). · Reason: it ships abstract PHPUnit test cases (`StorageConformanceTestCase`) that adapter packages extend. Core is unchanged. · Rejected: a framework-neutral assertion layer.
- 2026-10-25 · WP1 · Declarative input is bounded and grammatical, after the security review. Names use `\z`, not `$` (which admits a trailing newline). Query fields are a field name or a dotted path of names (`[A-Za-z][A-Za-z0-9_]*`), so `*`, `_source`, `_id` and Solr function or local-params syntax are refused everywhere a field appears, highlights included; `_score` is accepted only as `Sort::SCORE`. Schema field names may not start with `_`. Limits: page size 1000 and an offset that fits an int, `k` 10000, vector length and `dims` 4096, facet size 1000, terms 1000, string values 4096 bytes, bool filter depth 10, object field depth 10. Numbers must be finite. Language hints are ISO 639 codes. Messages quote and truncate echoed input. Values are literals: adapters compile them into structured queries, never into query strings. · Reason: agents and manifests construct these ASTs, and the compiled form reaches engine URLs and query DSLs; the limits are the engines' own ceilings (Elasticsearch's `k` and dims) or far above any real query. Deep-paging ceilings and per-field type checks against the schema are the adapters' and the compile step's (WP8). · Rejected: per-call overridable limits (no caller needs one yet); unbounded input relying on the engine to refuse.
- 2026-10-25 · WP1 · The storage contract is tightened, after the security review. Table and column names are developer constants, and every adapter still checks them with `Orion\Storage\Identifier` (`[a-z_][a-z0-9_]{0,62}`) before quoting; directions are exactly `asc` or `desc`; limit and offset are non-negative; `update()` and `delete()` refuse empty criteria; condition values are scalars, null or `DateTimeImmutable`. Orion's table definitions are checked by the same rule, and the `orion_index.schema` column is `definition` (`SCHEMA` is reserved in MySQL). The conformance case asserts all of it, plus bound values (`x' OR '1'='1` is stored and matched literally). The same-connection test now writes the entity through an abstract `insertOnHostConnection()` (the host's own connection) and the outbox row through the adapter, so an adapter holding a second connection fails it, which a mutation run confirmed. `InMemoryStorage` compares as SQL does: numbers numerically whatever their PHP type, dates as UTC instants. · Reason: drivers cannot bind identifiers, so the identifier rule is the injection boundary; the receipts table must not be wipeable through a generic call; a test that wrote both rows through the adapter could not detect the failure it was named for. · Rejected: an explicit `truncate()` (no caller); documenting the identifier rule without a conformance test.
- 2026-10-25 · WP1 · PHPStan runs with `treatPhpDocTypesAsCertain: false` (level 8 unchanged). · Reason: value objects re-check their phpdoc shapes at runtime (list, finite, element types) because callers without phpstan reach them; with phpdoc types treated as certain, phpstan reports those checks as always true. · Rejected: widening parameter types to `array` to make the checks look necessary.

- 2026-10-25 · WP2 · Three changes to the v1 §7 adapter contracts, made before the first engine adapter so no adapter is reworked: `WriteAdapter::delete(IndexName, Tombstone ...)` where a `Tombstone` carries the delete's outbox offset as its version; `SchemaAdapter::drop(IndexName)`; `SearchAdapter::raw(IndexName, callable $native, Filter ...$scope)`, whose neutral scope filters the adapter compiles and ANDs with the native query. - 2026-10-25 · WP2 · `EngineConformanceTestCase` (in `orion-search/testing`) defines the portable engine semantics: without an explicit sort, hits are compared as sets; `match` is analysed and case-insensitive (single-term behaviour only is promised; multi-term operators differ per engine), `term` is exact, `prefix` matches the start of a term, `phrase` needs adjacency and order; clauses and filters are conjunctive and `should` means at least one; a document carrying an undeclared field fails alone, with a `Failed` outcome, so no engine grows its mapping silently (dynamic mapping is off); applying a plan with breaking changes throws `LogicException`; a query with both lexical and vector retrieval on an engine without `HybridFusion` raises `UnsupportedClause` (core fuses those legs itself in WP8); each capability is asserted both ways, honoured when reported and refused with `UnsupportedClause` when not; version-stamped writes and tombstones converge in any arrival order (equal versions are stale). Every test runs on a fresh, randomly named index dropped afterwards. · Reason: v1 §18.1 makes conformance the gate between adapters; it can only assert what every engine can honour, and ranking is not deterministic (§17). · Rejected: asserting order for relevance-ranked results; letting engines map unknown fields dynamically.
- 2026-10-25 · WP2 · The dev `InMemory` engine lives in core (`Orion\Adapter\InMemory`) and passes the engine conformance suite: exact k-NN, facets, highlights, version-stamped writes with tombstones kept forever; no native fusion, nested documents, aliases or cursors. Without a sort it orders by score, then id, so development runs are repeatable; that is a property of this engine, never a promise of the AST. · Reason: revision §1 puts a dev engine in core so hosts and tests run without a service. · Rejected: a dev engine in `orion-search/testing` only (hosts want it in development, not just tests).
- 2026-10-25 · WP2 · `orion-search/pdo`: `PdoStorage` runs on the host's PDO and never reconfigures it (it refuses a connection not in `ERRMODE_EXCEPTION`, PHP's default since 8.0, instead of changing it); `transaction()` opens a transaction only when the connection has none, and otherwise joins the host's as a savepoint, so `Outbox::record()` inside an ORM's transaction commits and rolls back with it. Dates are bound as UTC with microseconds; identifiers are checked and quoted; `Installer::install()` creates only the tables the connection lacks. The storage conformance case gained `inHostTransaction()` and two tests for exactly that scenario; a mutation run (always `beginTransaction()`, as `polaris/pdo` does) fails both. A schema inspector and diff (revision §1) are deferred to the doctor checks that need them (WP5). · Reason: the same-connection invariant (revision §4) is only real if the adapter joins the transaction the host's code already opened; a skipped service-backed suite in CI would be a silent pass. · Rejected: setting `ERRMODE_EXCEPTION` on the host's connection; nesting by a private depth counter only.
- 2026-10-25 · WP2 · `orion-search/elasticsearch` supports Elasticsearch 8.19 and 9.x with client `^8.19 || ^9.0`; the host installs the client major matching its server (client 9 sends `compatible-with=9`, which 8.x refuses). - 2026-10-25 · WP2 · Hardening after the WP2 code and security reviews. (1) Under scope filters, a native body may use only keys that act within the matched documents (`query`, `knn`, `size`, `from`, `sort`, `_source`, `highlight`, `post_filter`, `track_total_hits`, `min_score`, `search_after`, `rescore`, `collapse`, `timeout`); anything that reads index-wide (aggregations, `global` in particular, suggesters, retrievers, runtime fields, script fields) is refused with `InvalidArgumentException`, because the scope becomes the tenant boundary in WP6; the filters are ANDed into every k-NN entry, a single or listed `knn` and `filter` alike, and no `match_all` is added beside a k-NN-only body (that would union every scoped document into it). Unscoped bodies are untouched: single tenancy keeps the full escape hatch. The conformance case gained `nativeShapes()` and `nativeScopeEscapes()` hooks to prove both per engine. (2) Highlight fragments are HTML-safe: the stored text is escaped and `<em>` is the only markup (Elasticsearch's `html` encoder; the in-memory engine escapes the same way); conformance asserts it. (3) Writing to or deleting from a missing index fails instead of letting Elasticsearch auto-create it with a dynamic mapping; bulk responses are trusted for nothing (outcomes keyed on the requested ids, an incomplete response fails every item, only a 2xx applies, 409 is stale, a 404 applies only for a delete without an error), and failure reasons are truncated. (4) `native('elasticsearch')` takes `settings` and `mappings` only, and cannot loosen `dynamic: strict` or overwrite Orion's `_meta`; `apply()` rewrites only Orion's `_meta` key. (5) Stemmers for folded text are named filters; a plan adding a field that needs an analyzer the live index lacks is refused by `apply()` with `LogicException`, as breaking plans are: core classifies it additive (it is, for engines that can add analysis), so WP3's planner must treat an adapter's refusal as "requires reindex". `MigrationPlan::applyTo()` moves the shared apply logic into core. (6) `Storage::update()` returns rows matched, changed or not; `PdoStorage` counts first on MySQL, which reports changed rows. Savepoint names are process-wide, so two storages on one connection never collide (MySQL silently replaces a same-named savepoint); a failing rollback never hides the exception that caused it; `Installer` refuses to run inside a MySQL transaction, which DDL would commit. (7) The in-memory engine now fails a document whose value its field type rejects (non-integer in `integer`, wrong vector dimensions) and honours `prefix` on keyword fields, matching Elasticsearch; conformance asserts both, `term` exactness, write-replaces-document, and delete-before-older-write. · Reason: each was a confirmed failure or divergence; the conformance case is where a portable promise lives, so each fix landed there first. · Rejected: a denylist of native keys (fails open on the next Elasticsearch feature); "rows changed" semantics for `update()` (differs per database).

- 2026-10-26 · WP3 · The index registry is one `orion_index` row per versioned physical index (`name` the physical index, `alias`, `engine`, `version`, `definition` as the declared `IndexSchema::toArray()` JSON, `schema_hash`, `created_at`; unique on alias and version) and one `orion_alias` row per alias (`alias`, `engine`, `physical`, `swapped_at`), written for every engine, native aliases or not. `IndexRegistration` is the row's declarative form: `fromRow()` refuses unknown columns, re-validates the definition through `IndexSchema::fromArray()` and refuses a definition whose hash does not match the stored one. · Reason: a reindex (v1 §8.3) builds version N+1 beside version N, so the registry must describe each physical index with its own schema, and receipts name `from_version` and `to_version`; recording the alias row on every engine gives core one answer to "what is current" (`AliasManager::current()`) for status, doctor checks and the determinism harness, with `AliasManager::target()` handing adapters the alias where the engine resolves it and the physical index where core keeps the indirection; the hash check makes a registry edit fail closed instead of steering the planner. · Rejected: a `physical` column on a one-row-per-alias `orion_index` (cannot hold the version being built); an alias row only on engines without native aliases (two code paths for "current").
- 2026-10-26 · WP3 · `MigrationPlan::between(desired, live, registered)` diffs what no live index reports, the org key and the per-engine `native()` settings, against the schema as registered, under the paths `_org_key` and `_native.<engine>` (field names cannot start with `_`, so they never collide); every such difference, an addition included, is breaking. A live index with no registration fails closed: whatever the desired schema declares there is breaking. An index that is neither live nor registered is a create and diffs nothing but its fields. Native settings compare canonically (keys sorted at every depth) and an empty object equals none. `Change::$before`/`$after` widened to `Field|array|string|null`, and `Change`, `MigrationPlan` gained `toArray()` for printing and comparison. · Reason: the WP1 carry-over; changing the tenant field or an engine's analysis settings can never be applied to a live index, and treating the registration as the only record of them keeps the plan a pure function of (desired, live, registered). · Rejected: a second list of setting changes beside the field changes (consumers would forget one); classifying a native addition as additive (no engine applies settings in place, and core classifies once for every engine).
- 2026-10-26 · WP3 · `IndexSchema::hash()` is sha256 over the canonical JSON of `toArray()`, the whole declaration, query-time attributes included, so equal declarations hash equal whatever order they were written in; `IndexSchema::named()` and `MigrationPlan::named()` re-address a declaration or a plan to the physical index behind an alias. · Reason: receipts (WP4) carry the schema hash of what was applied, and the registry compares it; the plan is computed for the alias the application names and applied to the physical index the engine knows. · Rejected: hashing only index state (a boost change would not change the registered schema).

(2) Adapters refuse a plan they cannot apply in place with `Orion\Adapter\RequiresReindex` (a `LogicException`, so the WP2 contract holds), thrown by `MigrationPlan::applyTo()` for breaking plans and by Elasticsearch for new analysis; the planner catches only it, so a programming error or a missing index no longer reads as "reindex required". - 2026-10-26 · WP4 · Outbox offsets come from a counter row, through a new `Storage::increment(table, criteria, column): ?int` that adds one to the single matching row and returns the new value (null when none matches, `LogicException` when several do). The row stays locked until the surrounding transaction ends, so offsets per index are dense and committed in order: a drain or replay reading `offset > cursor` can never miss a row that commits later with a lower offset, and a rolled-back write rolls its offset back too. Counters live in `orion_counter` (`name`, `value`): the outbox head per index (`outbox:<index>`), the drain cursors, the receipt sequence. `orion_outbox` is keyed on (`index_name`, `outbox_offset`) and unique on (`index_name`, `document_id`); its `id` column is gone. A PDO test proves the lock on PostgreSQL, MySQL and SQLite with a second connection that gives up waiting; the SQLite conformance run moved to a database file so a second connection sees the same database. · Reason: the WP1 carry-over; an identity column or a UUID v7 orders by allocation, not commit, so a reader can pass an offset whose transaction commits later, which loses that write; a compare-and-set retry loop reads a stale snapshot forever under MySQL's repeatable read; every host connection (PDO, Cycle, DBAL, Laravel) has `SET c = c + 1`. The cost is that writers to one index queue on its counter until they commit: correctness over write throughput, per index rather than global so indices do not contend. · Rejected: auto-increment or UUID ordering (allocation order); a sequencer assigning offsets after commit (needs commit order, which only the database knows); one global counter (every writer of every index queues behind one row); a dialect upsert in the port.
- 2026-10-26 · WP4 · The outbox is a compacted log: `Outbox::index(IndexName, id, fields)` and `Outbox::delete(IndexName, id)` take the index's next offset, delete the document's previous entry and insert the new one in one transaction (joining the host's as a savepoint), so `orion_outbox` holds exactly the latest write or delete of every document per index. The payload is the projected document as JSON (zero fractions kept, so `10.0` stays a float through JSONB and MySQL JSON); `Entry` is the row's declarative form (`fromRow()` refuses unknown columns, an unknown operation, a delete with a payload); `Entry::toDocument()` and `toTombstone()` carry the offset as the version. `Graph::outbox()` exposes it. Row helpers moved to `Support\Row`, which now reads stored dates as UTC whatever PHP's default zone (adapters store UTC; reading in the default zone was a latent bug in `IndexRegistration::fromRow()`); named counters go through `Storage\Counters` (`next()` in commit order, `advance()` forward only). · Reason: v1 §8.3 makes the database, through the outbox, the reindex source; a log keeping every write would grow without bound and make a full replay re-send every superseded version (and replaying a stale write after a delete is what Elasticsearch's `gc_deletes` window would otherwise have to cover), while a compacted log replays each document exactly once, at its latest state. Delete then insert, rather than an update, because MySQL's update count comes from a snapshot read; the index's counter lock serialises writers, so the insert never races. · Rejected: an append-only outbox with a separate pruner (unbounded until pruned, and replay re-sends history); storing only a reference and re-projecting at drain time (core cannot load host entities); a `Projector` dependency in the outbox (the projector is host code; the outbox takes its output).
- 2026-10-26 · WP4 · `Outbox\Drain` writes an index's entries in offset order and in batches to the index its alias points at (`AliasManager::targetOf()`: the alias on engines with native aliases, the physical index elsewhere), resolving the alias after each batch is read; its cursor is the counter `drain:<index>`, moved forward only, after the batch is written and in one storage transaction with the batch's dead letters. A run stops at the head it saw when it started and reports `DrainResult` (from, to, head, lag, applied, stale, failed); an index whose alias Orion has not built waits with its lag reported. `Outbox\Delivery` sends entries as documents and tombstones versioned by offset and accounts for every entry by id, so an entry the engine reports nothing for is a failure, never a write. Per-document failures go to `orion_dead_letter` (one row per entry: error truncated to 2000 bytes of valid UTF-8 by the new `Assert::truncate()`, attempts, failed_at); `DeadLetters::retry()` resends them, and a letter is cleared when its entry or any newer entry of the same document reaches the index, or when compaction removed its entry. Two ports join `Config` as nullable named parameters, closing the WP1 carry-over for them: `Outbox\Dispatcher::dispatch(IndexName)` (core default `SyncDispatcher`, which drains at once; call it after the recording transaction commits, never inside it) and `Observability\Metrics` with `counter()` and `gauge()` (core default `NullMetrics`; the drain reports `orion.outbox.applied`, `.stale`, `.failed` and the `.lag` gauge per index). `orion-search/testing` gains `FaultyEngine` (kill before or after a verb, or mid-bulk after N documents), `EngineKilled` and `SettableClock`. · Reason: v1 §10 and §8.3: a killed engine must cost a retry, never a document, so the cursor trails the engine; resolving the alias after reading a batch means any entry read after a swap commits goes to the new index, which is what lets the reindexer's final catch-up close the swap window (next entry). A dispatcher cannot run inside the host's transaction because the drain would write documents the host may still roll back, and core cannot hook the host's commit, so the call is the host's (or the module's after-commit listener). The metrics port is Polaris's `counter()` plus `gauge()`, because lag is a level, not a count. · Rejected: advancing the cursor before writing (loses the batch on a crash); writing to the physical index on every engine (an engine alias moved without its row, the mid-swap failure, would then split reads from writes); recording the dispatch inside `Outbox::index()`; a dead-letter table keyed by document (loses which version failed).
- 2026-10-26 · WP4 · Receipts. `Receipt\Receipt` records one lifecycle operation: `sequence`, `operation` (`Lifecycle\Operation`, which gains `reindexed` and `dropped`), `index` (the alias), `engine`, `from_version` (null for a create), `to_version`, `document_count`, `schema_hash`, `from_offset`, `to_offset`, `previous_hash`, `hash`, `kid`, `signature`, `recorded_at`. Its message is the canonical JSON of every field but `hash` and `signature` (time as UTC with microseconds), `hash` is that message's sha256 and `signature` an Ed25519 signature over the message, base64. `orion_receipt` is keyed on `sequence` (the `id` column is gone, so two identical runs produce identical receipts), versions are integers, and `engine` is new. `ReceiptStore` only appends and reads: the sequence comes from the `receipt` counter, whose lock serialises appends so each chains to the receipt committed before it and the chain cannot fork, and it refuses to extend a chain whose previous receipt is missing. `Verifier` walks the chain and reports, per receipt, a hash that does not match its contents, a gap in the sequence, a `previous_hash` that is not the previous receipt's hash, and a signature that does not verify under its kid, plus a chain that ends before the last sequence issued (truncation). `ReceiptSigner` is the port (`kid()`, `sign()`, `verify(message, signature, kid)`), joining `Config` as a nullable named parameter; `SodiumSigner` takes a 64-byte secret key, a seed or base64 key material, plus earlier kids' public keys so receipts signed before a rotation still verify, marks key parameters `#[SensitiveParameter]` and shows only its kid when dumped. The planner appends a receipt for `created` and `applied`, inside the storage transaction that swaps the alias or updates the registration, so neither commits without its receipt (a create whose receipt fails is released like any failed create); `unchanged` and `reindex_required` change nothing and are not receipted. `Outcome` carries the receipt. A query-time change (a boost) now reports `applied`, not `unchanged`: it changes the registered schema, which receipts attest. The determinism harness compares receipts across runs and verifies the chain; the storage conformance case proves a chain round-trips and verifies on each database, microseconds included. · Reason: revision §3 and v1 §11: the chain makes an edit, removal or reorder evident, the signature makes a rewrite need the key, and the sequence counter makes cutting the tail evident. Without a signer the lifecycle still runs and issues no receipts: a key is a deployment secret core cannot invent, and an ephemeral or database-held key would sign receipts that prove nothing; this is how "core default: Ed25519 through libsodium" is read here (the implementation is core's, the key is the host's), and the doctor check (WP5) warns when receipts are off. · Rejected: an ephemeral key generated at boot; a key stored beside the receipts; unsigned receipts with an empty signature; signing the hash instead of the message (verifiers then trust the hash function twice); a UUID per receipt (identical runs could not produce identical receipts).
